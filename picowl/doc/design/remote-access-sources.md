# Remote access research: the evidence behind the proposal

**Status:** appendix to [remote-access.md](remote-access.md), written 2026-10-06. It keeps what the five research sweeps found, claim by claim with the source each one cites, and the skeptic's review of the decisive claims, so that the proposal can be checked and the research can be repeated or extended. The sweeps were done by model agents reading the web and the picowl source; the skeptic reopened the sources of the claims that carry the decision. A [read] tag means an agent read it at the URL; it does not mean the claim was independently re-read unless the skeptic review below says CONFIRMED. Treat [inf] as an estimate and [unknown] as open.

## Sweep 1: Remote-access software landscape for a wlroots compositor on an ARMv5 no-FPU handheld (h2200, bt-pan)

- **[read]** wayvnc is the standard VNC server for wlroots compositors. ISC licence. Required deps (meson.build master, version 0.11-dev): pixman-1, libdrm, xkbcommon >=1.0, wayland-client, jansson, aml >=1.0 <2.0, neatvnc >=1.1 <2.0. Optional: libpam, gbm (only for the screencopy-dmabuf option), scdoc. It has no libjpeg, gnutls or ffmpeg dependency of its own; those come in through neatvnc. (https://raw.githubusercontent.com/any1/wayvnc/master/meson.build)
  - Why it matters: All of these build in OE, but it is a separate client process that needs a Wayland socket, so it competes with picowl for the 400 MHz CPU. The build can be trimmed to shm only.
- **[read]** wayvnc releases: v0.10.2 (2026-09-25), v0.10.1 (2026-07-09), v0.10.0 (2026-04-28), v0.9.1 and v0.9.0 (2024-11), v0.8.0 (2024-02). Release dates are from the GitHub API. The release-notes page gave no year. v0.9.0 added ext-image-copy-capture-v1 and CMA-backed buffers for Raspberry Pi hardware encoding. v0.10.0 added multi-output capture and legacy DES auth for RFB 3.3/3.7 clients. Actively maintained, one main author (any1). (https://api.github.com/repos/any1/wayvnc/releases?per_page=6 ; https://github.com/any1/wayvnc/releases)
  - Why it matters: Alive and current. It supports ext-image-copy-capture, so it will not need wlr-screencopy forever. wlr-screencopy v3 still works today and is already in picowl.
- **[read]** wayvnc capture path: it tries dmabuf first when built with ENABLE_SCREENCOPY_DMABUF and the compositor offers linux_dmabuf, otherwise it falls back to wl_shm. It uses zwlr_screencopy copy_with_damage (v2+) and the ext-image-copy-capture damage_buffer, and passes the received damage on to neatvnc. Capture is rate-limited with --max-fps (default 30), driven by an aml timer. Options include -o/--output, -r/--render-cursor, -d/--disable-input, -p/--show-performance, a control socket (wayvncctl) and ws: WebSocket address prefixes. (https://raw.githubusercontent.com/any1/wayvnc/master/src/screencopy.c ; .../src/ext-image-copy-capture.c ; .../wayvnc.scd)
  - Why it matters: With dmabuf compiled out and --max-fps 2..5, wayvnc runs on the shm path. Each capture still costs a CPU read of the output buffer. picowl's doc/capture.md already warns this is slow on write-combined dumb buffers. Damage plumbing exists end to end.
- **[read]** wayvnc security: VeNCrypt (TLS with X509 and user/password), RSA-AES (trust on first use), and legacy DES VNC auth (needs allow_broken_crypto). It listens on localhost only by default. The README mentions compatibility concerns with macOS Screen Sharing. (https://github.com/any1/wayvnc ; https://raw.githubusercontent.com/any1/wayvnc/master/README.md)
  - Why it matters: For bt-pan or usb0 you must set the address and an auth mode. TLS means gnutls in neatvnc (extra CPU for the handshake). RSA-AES needs nettle, hogweed and gmp. DES or no auth over a point-to-point USB link is the cheapest option. On macOS, the built-in Screen Sharing client has known auth quirks with non-Apple servers.
- **[read]** neatvnc (the RFB library under wayvnc) is ISC licensed and currently 1.1-dev on master. Releases: v1.0.3 (2026-10-03), v1.0.2 (2026-09-25), v1.0.1 (2026-07-09), v1.0.0 (2026-04-28) (GitHub API dates). The v1.0.0 release notes mention RFB 3.3/3.7 and DES auth. Required deps: pixman-1, zlib, aml (>=1.0 <2.0), libdrm headers. Optional meson features, all auto by default: jpeg (libturbojpeg), tls (gnutls), nettle (nettle, hogweed, gmp; also needed for WebSocket), gbm, h264 (ffmpeg or V4L2 m2m, which needs gbm and libdrm). Setting -Djpeg=disabled -Dtls=disabled -Dnettle=disabled -Dgbm=disabled -Dh264=disabled leaves pixman, zlib and aml only. (https://raw.githubusercontent.com/any1/neatvnc/master/meson.build ; .../meson_options.txt ; https://api.github.com/repos/any1/neatvnc/releases?per_page=4)
  - Why it matters: This is the key finding. The minimum OE dependency set is pixman, zlib and aml, plus libdrm headers. pixman and zlib are already on the image, and aml is a small library.
- **[read]** neatvnc encodings: src/enc/ contains raw.c, tight.c, zrle.c and h264 (ffmpeg, v4l2m2m, openh264). choose_frame_encoding() picks the first of RAW, TIGHT, ZRLE that the client lists, then H.264 for GBM buffers, and falls back to RAW. There is no Hextile or RRE. CopyRect is listed but not used for output (reading of the source, not run). ZRLE: raw deflate level 1, memLevel 9, 64x64 tiles, damage-aware, uses 2 aml worker threads. Tight: 64x64 tiles, 4 deflate streams, JPEG only when libturbojpeg is built in and quality <10, basic = deflate. The source gives RGB565 in Tight no explicit support. Pixel formats go through DRM fourcc conversion, and the client's negotiated pixel format (including 16 bpp and palette via RGB332) is honoured. (https://raw.githubusercontent.com/any1/neatvnc/master/src/server.c ; .../src/enc/zrle.c ; .../src/enc/tight.c)
  - Why it matters: On a 400 MHz no-FPU CPU, ZRLE at deflate level 1 on damage-only tiles is the sensible choice, and a client asking for Raw or ZRLE with 16 bpp avoids conversion. zlib level 1 cost on PXA255 is unmeasured [unknown]. Without CopyRect, scrolling sends pixels. Tight without JPEG is deflate only. 'Worker threads' on a single core mean no speedup, only context switches.
- **[read]** neatvnc flow control: bandwidth estimation with a cap on inflight bytes (frames are dropped if inflight_bytes exceeds max_inflight), and a max delay of about 33.3 ms plus RTT. Continuous updates are supported. Non-incremental requests union the damage. The code uses double for this estimate and for rate_pixel_format scoring. (https://raw.githubusercontent.com/any1/neatvnc/master/src/server.c)
  - Why it matters: It adapts to a slow link by dropping frames, which suits bt-pan. Floating point appears only in per-frame bookkeeping, so softfloat cost should be negligible [inf, not measured]. The 33 ms ceiling is too aggressive for a 90 kB/s link, and may need a patch or a lower --max-fps.
- **[read]** neatvnc embedding API (master header): nvnc_new, nvnc_listen_tcp/unix, nvnc_display_new/nvnc_add_display, nvnc_frame_from_raw(buffer,w,h,fourcc,stride) or nvnc_frame_new, nvnc_frame_set_damage(frame, pixman_region16*), nvnc_display_feed_frame, plus nvnc_set_key_fn, nvnc_set_pointer_fn and nvnc_set_cursor callbacks. Auth: nvnc_enable_auth, nvnc_set_tls_creds, nvnc_set_rsa_creds. (https://raw.githubusercontent.com/any1/neatvnc/master/include/neatvnc.h)
  - Why it matters: picowl could link neatvnc directly and feed it the pixman buffer it already renders into. The damage region comes straight from the scene, with no screencopy round trip, no extra process and no extra copy. Pointer events map to the existing virtual-pointer path and key events to the virtual keyboard. This needs a small picowl module, not a new protocol server.
- **[read]** Weston ships a VNC backend built on neatvnc (config: [vnc] refresh-rate, tls-key, tls-cert; [output] name=vnc, mode, resizeable). The man page states it runs without graphics hardware or input devices. It was added by merge request 362 (could not read the MR page, Anubis block). Weston also has an RDP backend on FreeRDP: RemoteFX is on by default, with NSCodec or raw bitmap fallback, and TLS or RDP security. (https://www.mankier.com/7/weston-vnc ; https://www.mankier.com/7/weston-rdp ; https://gitlab.freedesktop.org/wayland/weston/-/merge_requests/362 (search snippet only))
  - Why it matters: This is existing proof that a compositor embeds neatvnc directly. It is also the pattern to copy. Weston itself is not an option (picowl is a wlroots compositor). Weston RDP requires FreeRDP, which is far heavier.
- **[read]** wlroots screencopy v1 behaviour (master mirror source): frame copy fails when the output is not enabled (checks in frame_handle_copy and capture_output; the frame also fails if the output is disabled after creation). It schedules an output frame (wlr_output_schedule_frame) and reads SHM pixels with wlr_renderer_read_pixels after the commit. A Hyprland forum thread reports that with DPMS off, screencopy streams freeze because the output stops rendering and frame callbacks stop. (https://git.nixnet.services/blankie/wlroots/raw/branch/master/types/wlr_screencopy_v1.c ; https://forum.hypr.land/t/screencopy-with-dpms-off/167)
  - Why it matters: The user's requirement matters here. Simply blanking or disabling picowl's real output, as the power code already does with output_commit_disable, makes the wlr-screencopy path fail for wayvnc. Blanking the backlight but keeping the commit running still uploads to the MediaQ. The 'remote mode' therefore cannot be just DPMS off plus wayvnc. It needs either an in-process neatvnc feed or a different output to capture. Read from a master mirror, not the 0.19.0 tag (gitlab and the tag URLs blocked). Verify against the 0.19 source in subprojects.
- **[read]** wlroots 0.19.0 added ext-image-capture-source-v1 and ext-image-copy-capture-v1 (release coverage). The 0.19 headless backend can add outputs (wlr_headless_add_output) and can be created with an existing renderer (wlr_headless_backend_create_with_renderer). The source file URLs for the 0.19.0 tag returned 404, so the claims come from search snippets and the header mirror. (https://linuxiac.com/labwc-0-9-wayland-compositor-released-with-wlroots-0-19-support/ ; https://git.nixnet.services/blankie/wlroots/src/branch/master/include/wlr/backend/headless.h)
  - Why it matters: A design option follows (inference): in remote mode, picowl moves the scene to a headless output backed by pixman memory, disables the DRM output (no MediaQ upload), and captures from the headless output. A headless output renders into RAM and has no hardware to upload to. This needs a picowl output hotplug and move path, and picowl already uses the headless backend for tests. picowl lacks ext_image_copy_capture, which is only needed if the capture client is wayvnc and not an in-process neatvnc.
- **[inf]** Inference on the display-disable requirement: the cheapest zero-MediaQ remote path is an in-process neatvnc feed of the already composited RAM buffer. picowl's commit loop (src/output.c output_frame -> wlr_scene_output_commit) renders damage into the pixman buffer first and the kernel DRM driver then uploads it. In remote mode, skip the DRM commit (or disable the output) after composition and keep rendering into an offscreen/headless buffer so frames and damage keep flowing. picowl already has output_commit_enable/disable and a blank state in power.c. (/Users/koen/Projects/Angstrom/Tiny-UI-research/picowl/src/output.c ; /Users/koen/Projects/Angstrom/Tiny-UI-research/picowl/doc/capture.md)
  - Why it matters: This is a design recommendation, not tested. Two routes: (A) headless output swap, which works with unmodified wayvnc via wlr-screencopy and no new picowl protocol code but needs output-move logic; (B) built-in neatvnc plus a render-only mode, which is less code per frame and removes a process (and a second wl_shm copy), but picowl links neatvnc. In both, the real output must be disabled or the display powered down only after the frame source is switched.
- **[read]** 32-bit ARM evidence for wayvnc: Alpine publishes wayvnc for armhf (hard-float, ARMv6+), and Debian builds wayvnc 0.10.1-1 for armhf (installed on arm-conova-03). Debian's amd64 package is 82.7 kB with 275.0 kB installed. Debian's build status list does not include armel (ARMv5 soft-float). No report found of wayvnc or neatvnc on ARMv5, or on any CPU without an FPU, and no memory-footprint numbers documented. (https://packages.debian.org/sid/wayvnc ; https://buildd.debian.org/status/package.php?p=wayvnc ; https://pkgs.alpinelinux.org/package/v3.17/community/armhf/wayvnc)
  - Why it matters: Nothing known blocks a soft-float ARMv5 build. The code is plain C11 with pixman and zlib, but it is untested there [unknown]. The 275 kB installed size is the binary only; RSS with the framebuffer and zlib state is unmeasured [unknown].
- **[read]** LibVNCServer: GPLv2 (linking makes derivative work), releases 0.9.15 (2024-12-22), 0.9.14 (2022-12-18), 0.9.13 (2020-06-13). Encodings: Raw, CopyRect, RRE, CoRRE, Hextile, Zlib, Tight, Ultra, TRLE, ZRLE, ZYWRLE, TightPNG. Crypto: OpenSSL, libgcrypt or a bundled light implementation; TLS via OpenSSL or GnuTLS; also zlib, libjpeg, libpng, libsasl and WebSocket support. CMake build. Android cross-build documented. It has no Wayland capture, so it would need a screen grabber written around it, and it is a library to be embedded. (https://github.com/LibVNC/libvncserver ; https://api.github.com/repos/LibVNC/libvncserver/releases?per_page=3)
  - Why it matters: It has the broadest encoding set including Hextile and CopyRect and runs on tiny machines historically (inferred from its long embedded use, not read). GPLv2 versus picowl's licence needs checking (LICENSE file not read). Maintenance is slower: about one release a year or two. Plausible as an embeddable alternative to neatvnc, but it offers no Wayland integration and more optional deps.
- **[read]** FreeRDP is Apache licensed, 25,525 commits, with CI for ARM, PowerPC and RISC-V; it has a server library and shadow server. Weston's RDP backend uses it with RemoteFX, NSCodec or raw bitmap updates. I did not get dependency lists, footprint or a release date. RemoteFX is a wavelet codec and needs real CPU (no figures found). (https://github.com/FreeRDP/FreeRDP ; https://www.mankier.com/7/weston-rdp)
  - Why it matters: RDP codecs and RemoteFX would be too heavy for a 400 MHz no-FPU CPU. Raw bitmap updates would work but add nothing over VNC. Clients exist on macOS and iOS (Microsoft Remote Desktop, claimed from memory, not checked). Ranked unsuitable as a first choice.
- **[inf]** gnome-remote-desktop and KRDP/krfb (KDE) are tied to their compositors through PipeWire, xdg-desktop-portal and the compositor's own screencast and input APIs (from general knowledge, no source fetched). wayvnc's own README says GNOME, KDE and Weston are not supported. (https://github.com/any1/wayvnc)
  - Why it matters: Not usable on picowl. Reading them for completeness only. Searches for sources on these did not return usable pages.
- **[read]** SPICE: libspice-server1 (Debian 0.15.1-1 builds exist for armhf) depends on glib2, gstreamer, libjpeg, liblz4, libopus, orc, pixman, sasl2 and zlib. It targets virtual machines (QEMU/libvirt), and I found no Wayland compositor integration or tiny-device use. (https://blueprints.launchpad.net/ubuntu/mantic/armhf/libspice-server1/0.15.1-1 ; https://packages-picconi.debian.org/ja/buster/libspice-server1)
  - Why it matters: Large dependency chain (glib and gstreamer) for no benefit. Unsuitable.
- **[read]** Waypipe is a Wayland protocol proxy (forwards app windows, not the whole screen). Since 0.10.3 (March 2025) it is a Rust rewrite, GPLv3, using libzstd, liblz4 and (for video) libavcodec/libswscale; Vulkan replaces libgbm. Source repository pages blocked (Anubis); details via distro changelogs and spec only. (https://src.opensuse.org/pool/waypipe/raw/branch/factory/waypipe.changes)
  - Why it matters: Opposite direction: it would run the apps on the Mac or Linux box and show them on picowl, or run handheld apps on a remote Wayland display. It does not mirror the picowl screen or panel and needs a Rust toolchain on ARMv5 (Rust has armv5te-unknown-linux-gnueabi as a target, not verified here). Not a fit for the wish (watch and control the handheld), but note its use for running heavy apps remotely.
- **[read]** noVNC (MPL 2.0) is an HTML VNC client for browsers. Its client supports Raw, CopyRect, RRE, Hextile, Tight, TightPNG, ZRLE, JPEG, Zlib and H.264. It needs a WebSocket endpoint: either the server speaks it natively (neatvnc/wayvnc WebSocket needs nettle) or websockify (a separate proxy) runs on the viewing host. Minimum browsers: Chrome 89, Firefox 89, Safari 15, Edge 89, Opera 75. (https://github.com/novnc/noVNC)
  - Why it matters: Good for the Mac and iOS (Safari) without installing a client. Run websockify and noVNC on the peer machine, never on the handheld, which keeps the extra code and WebSocket cost off the PXA255. Both noVNC and wayvnc are alive.
- **[read]** Clients: macOS has a built-in Screen Sharing VNC client, and RealVNC (iOS, Mac, Linux, Pi) and TigerVNC (Mac, Linux, Windows, BSD) exist. TigerVNC supports a Tight variant accelerated with libjpeg-turbo. The detail that Apple's client needs DES or ARD auth could not be confirmed beyond wayvnc's README hint. I did not find a verified list of iOS clients and their encodings (Screens, bVNC etc. not checked). (https://speedtesthq.com/guides/protocols/what-is-vnc ; https://flathub.org/apps/org.tigervnc.vncviewer)
  - Why it matters: Client side CPU is irrelevant, but the encodings the client advertises decide what neatvnc sends. Test with TigerVNC (ZRLE, Raw) and noVNC first. A client lists its preferred order; neatvnc takes the first of Raw, Tight, ZRLE in the client's order. Some clients list Tight first, which gives deflate-only Tight, and a client that asks for Raw first would get raw over bt-pan.
- **[read]** RFB (RFC 6143) sizes: ProtocolVersion 12 bytes; security list 1 byte count plus types; VNC auth 16-byte DES challenge/response; SecurityResult 4 bytes. Client messages: SetPixelFormat 20 bytes, SetEncodings variable, FramebufferUpdateRequest 10, KeyEvent 8, PointerEvent 6, ClientCutText variable. FramebufferUpdate: 4-byte header, then per rectangle 12 bytes (x,y,w,h as 2 bytes each, encoding 4 bytes). Encodings: Raw, CopyRect, RRE, Hextile (16x16 tiles), ZRLE (zlib, 64x64 tiles). The RFC lists Tight as a historic assignment. (https://www.rfc-editor.org/rfc/rfc6143)
  - Why it matters: A tiny server needs only the 3.8 handshake with None or VNC auth, ServerInit, a message loop on 6 client message types, and Raw/CopyRect/Hextile/ZRLE writers. A full Raw 240x320 RGB565 update is 153,600 bytes plus 16 bytes header, so about 1.7 s at 723 kbit/s (inference below).
- **[read]** Small RFB servers exist: uVNC (Micro-VNC) ran with uIP on 8-bit systems including a Commodore 64; rfbcounter is a single C file plus headers, RRE only, with no framebuffer, and its author says it is 'not an example of good VNC code'; SEGGER emVNC is a commercial ANSI C server with optional Hextile and 'very low memory footprint' but no footprint figures in the manual, no licence terms, no Wayland. fbvnc (zohead) exists on GitHub (a client, not read). (https://www.staff.uni-mainz.de/tacke/VNC/rfbcounter.html ; https://doc.segger.com/UM22001_emVNC.html ; https://www.github.com/zohead/fbvnc)
  - Why it matters: Shows a minimal RFB server is a few hundred lines of C, feasible without any library. I did not find a measured size for a Raw+CopyRect+Hextile+ZRLE implementation, so my size estimate below is [inf]. zlib is already linked via pixman/png elsewhere on the system.
- **[inf]** Estimate for a purpose-built server (inference, not measured): handshake, ServerInit and message loop with no auth or VNC auth about 300 to 500 lines of C; Raw plus Hextile writers about 150 more; ZRLE with zlib about 200 more; DES for VNC auth needs a small DES (about 150 lines) or can be skipped; CopyRect needs the compositor to report scroll moves, which the damage model does not provide. Total about 800 to 1200 lines, all integer arithmetic, plus zlib (already in the image).
  - Why it matters: Fits a 400 MHz no-FPU CPU, needs no aml thread pool, no libdrm, no gnutls and can run inside the picowl event loop. Cost: you own the code (security review, client quirks, RFB 3.3 clients) which neatvnc already handles.
- **[inf]** Link budget (inference with stated assumptions): Bluetooth 1.x ACL tops out at 723.2 kbit/s one way (DH5), EDR at about 1.45 or 2.18 Mbit/s (2-DH5/3-DH5) before L2CAP, BNEP and IP/TCP overhead. These are textbook figures from memory, not read. A full 240x320 RGB565 frame (153,600 B) is therefore at least 1.7 s uncompressed at 723 kbit/s and about 0.85 s at 1.45 Mbit/s. Practical PAN throughput measurements were not found: two papers surfaced by search (UCL LCS2005/67, Luque 2015) could not be read (garbled PDF, 403). The h2200's Bluetooth version and radio chip was not established here.
  - Why it matters: Raw is unusable over bt-pan except for tiny damaged rectangles. Compression (ZRLE on a mostly flat UI) plus low frame rate plus dropping frames is mandatory. A USB gadget link (usb0) is far faster but its measured throughput is also unknown.
- **[unknown]** The CPU cost on PXA255 is the unknown that decides the ranking. No source gives zlib level 1 deflate speed, ZRLE encode speed or Hextile cost on PXA255 or any ARMv5 core; the MediaQ bus figure of 7.9 to 9.1 MB/s is from the task. A rough rule (inference): zlib deflate level 1 runs in the order of 10s of MB/s on 1 GHz-class ARM and several times less on 400 MHz ARMv5 with a 32 KB data cache, so one 153,600 B frame is plausibly 20 to 60 ms of CPU. That figure is a guess and should be measured with a one-off benchmark on the device.
  - Why it matters: Benchmark zlib level 1 on the h2200 with real UI frames before choosing between ZRLE and Hextile. Cheap to do and decides whether built-in neatvnc or a custom Hextile-only server is better.

## Sweep 2: RFB encodings, pseudo-encodings and per-frame CPU/bandwidth cost at 240x320 on a 400 MHz ARMv5TE without FPU (h2200 over bt-pan)

- **[inf]** Frame size arithmetic. 240x320 = 76,800 px. RGB565 raw = 153,600 B; 8 bpp raw = 76,800 B; 32 bpp raw = 307,200 B. At 480x640 (hx4700) the same figures are 4x. Raw-update time on the link is size / link rate: 153.6 KB takes about 1.9 s at 80 KB/s and 6.1 s at 25 KB/s. A 240x16 text-line strip at 16 bpp is 7,680 B, about 0.1 to 0.3 s at those rates. (Arithmetic from the task's own numbers. Link rates taken from the LKML entry below.)
  - Why it matters: A full-frame Raw update is not viable on bt-pan. Only damage-driven small rectangles, or compressed ones, are. Anything with continuous full-screen change (video) cannot be shown at full rate whatever the encoding.
- **[read]** Measured Linux BNEP/PPP throughput is low, in 2005 kernel-list reports: about 80 KB/s Linux-to-Linux, 25 KB/s with a USB dongle plus Nokia 6230 (over RFCOMM/PPP), and 10 KB/s with a Billionton PCMCIA/CF card, which was also throwing 'bnep0: transmit timed out' watchdog errors. These are anecdotal, from 2005, and the 25 and 10 KB/s cases were not plain PAN. Real bt-pan rates for the h2200's own Bluetooth chip and for EDR are [unknown] in what I found. (https://lkml.iu.edu/hypermail/linux/kernel/0510.2/1515.html)
  - Why it matters: Use roughly 10 to 80 KB/s as the planning range for bt-pan. It needs to be measured on the real device with iperf.
- **[read]** RFC 6143 gives the baseline semantics. Raw must be supported by all clients and is pixel data in scan-line order. CopyRect is only source coordinates. RRE and Hextile are 'obsolescent'. TRLE and ZRLE are tiled with palettes and run-length coding, and ZRLE adds zlib. SetPixelFormat lets the client pick the pixel format so as to balance speed against bandwidth, and the server must be able to supply it. An incremental FramebufferUpdateRequest means 'send me only changes, when there are any', and the RFC says the slower the client and network, the lower the update rate, because updates are request-driven. The Cursor pseudo-encoding makes the client draw the cursor locally. DesktopSize signals a changed framebuffer size. (https://www.rfc-editor.org/rfc/rfc6143 and https://raw.githubusercontent.com/rfbproto/rfbproto/master/rfbproto.rst (the newer community spec that also covers the extensions; the WebFetch tool truncated it, so I downloaded and grepped the raw file))
  - Why it matters: The request-driven model already gives coalescing for free. When bt-pan is slow, damage accumulates and the next update is bigger but less frequent.
- **[read]** ZRLE (spec) uses 64x64 tiles. A single zlib stream is shared for the whole connection, so rectangles must be encoded and decoded strictly in order. A CPIXEL is 3 bytes for 32 bpp/depth 24, but with a 16 bpp or 8 bpp pixel format it is 2 or 1 byte. The spec says the client is 'much better off using 16 or even 8 bits-per-pixel'. Tile subencodings: solid, packed palette up to 16 colours, plain RLE, palette RLE, raw. The persistent zlib stream means no per-rectangle dictionary reset, so many small rectangles compress well across updates. (https://raw.githubusercontent.com/rfbproto/rfbproto/master/rfbproto.rst (section ZRLE Encoding))
  - Why it matters: This is the best fit for crisp-font terminal and bar content, which has few colours. The shared stream is a single-threaded dependency, which is fine on one core.
- **[read]** Tight (spec). Rectangle width is at most 2048. There are three methods: BasicCompression (zlib, 4 streams, filters Copy, Palette (2 to 256 colours, 1-bit packing for 2 colours) and Gradient (16 and 32 bpp only)), FillCompression (one solid colour) and JpegCompression (only at 16 or 32 bpp, and only if the client advertised a JPEG quality pseudo-encoding). Data under 12 bytes after filtering is sent uncompressed. TPIXEL is 3 bytes at 32 bpp/depth 24. There is also a 'Tight Encoding Without Zlib' pseudo-encoding that lets the server skip zlib for basic rectangles. (https://raw.githubusercontent.com/rfbproto/rfbproto/master/rfbproto.rst (Tight Encoding, JPEG Quality Level Pseudo-encoding, Tight Encoding Without Zlib))
  - Why it matters: Tight with the palette filter is comparable to ZRLE for UI. JPEG is the only practical path for photo or video content. 'Without zlib' would let a CPU-starved server send Tight with no deflate, but client support for it is [unknown].
- **[read]** Pseudo-encoding numbers. Compression Level -247..-256 (-247 is high compression, -256 low) is only a hint. JPEG Quality -23 (high) .. -32 (low). JPEG Fine-Grained Quality -512..-412 (0 to 100). JPEG Subsampling -768..-764 (1X, 4X, 2X, grayscale, 8X). ContinuousUpdates -313, with message 150 EnableContinuousUpdates and EndOfContinuousUpdates. Fence is -312. QEMU Extended Key Event is -258. Extended Clipboard is 0xc0a1e5ce. Hitachi ZYWRLE is 17. TRLE is 15. H.264 is 20. Open H.264 is a separate id. TightPNG is -260. (https://raw.githubusercontent.com/rfbproto/rfbproto/master/rfbproto.rst (pseudo-encoding tables))
  - Why it matters: Reference for the picowl server and for client option lists. Setting low compression level and the JPEG pseudo-encodings is how a client asks a weak server to trade bandwidth for CPU.
- **[read]** ContinuousUpdates, per spec. A client that sees the ContinuousUpdates pseudo-encoding confirmed enables it with message 150 for a rectangle. The server then pushes updates for that area as damage occurs, and must ignore incremental update requests while it is active. Non-incremental requests are still honoured. The spec says a fast client may rate-limit its own incremental requests to avoid hogging the network. (https://raw.githubusercontent.com/rfbproto/rfbproto/master/rfbproto.rst (EnableContinuousUpdates, ContinuousUpdates Pseudo-encoding, FramebufferUpdateRequest))
  - Why it matters: With ContinuousUpdates plus Fence, the server can see round-trip time and pace itself. Without them it is paced by the viewer's request rate.
- **[read]** neatvnc v1.0.3 (released 2026-10-03). Encodings it will pick: only Raw, Tight and ZRLE. The code accepts Copyrect, RRE, Hextile and TRLE in SetEncodings but the encoder-selection loop returns only RAW/TIGHT/ZRLE in the client's preference order, with RAW as the fallback. It handles pseudo-encodings Cursor, DesktopSize, ExtendedDesktopSize, QEMU ext key, Extended Clipboard, ContinuousUpdates, ExtMouseButtons and Fence. There is no ZYWRLE. neatvnc does not use the CopyRect and Hextile encoders at all. (https://raw.githubusercontent.com/any1/neatvnc/master/src/server.c and https://api.github.com/repos/any1/neatvnc/releases/latest)
  - Why it matters: neatvnc is the natural library for a wlroots compositor, because it is what wayvnc uses. Its encoder set (Raw, ZRLE, Tight+optional JPEG) is adequate but not tuned for a slow CPU.
- **[read]** neatvnc ZRLE: zlib level 1 and memLevel 9. Tiles are 64x64. Palette is at most 16 colours, built per pixel with memcmp over the palette (src/enc/zrle.c: find_colour_in_palette, 'if (n >= 16) return -1'). Solid tiles have a dedicated path. Tiles are encoded independently with no inter-frame comparison. Integer-only code, no SIMD and no floating point. It uses the aml worker threads (two workers, via parallel-deflate), which is pointless on a single core but harmless. (https://raw.githubusercontent.com/any1/neatvnc/master/src/enc/zrle.c)
  - Why it matters: The code uses no FPU or NEON, so it should build and run on ARMv5. A per-pixel memcmp palette search is slow on this CPU. A hand-written 16-bit specialisation is probably worth a few ms per frame (see the estimates below).
- **[read]** neatvnc Tight: 64x64 tiles, zlib level 1, four zlib streams (tile column mod 4). JPEG exists only when built with libturbojpeg. It is used only when the client sent a JPEG quality pseudo-encoding (internal quality 0 to 9). The default is quality=10, which means no JPEG. The JPEG call uses TJFLAG_FASTDCT, with 4:2:0 subsampling (4:4:4 at quality 9). The code converts the 32-bit format to BGR888 for Tight. (https://raw.githubusercontent.com/any1/neatvnc/master/src/enc/tight.c)
  - Why it matters: Tight in neatvnc is a 2-bpp-unfriendly path (24-bit conversion) and gives no palette filter that I could see. ZRLE is the better lossless choice. Tight+JPEG is the video/photo option, and it needs libturbojpeg built without NEON/SIMD for ARMv5.
- **[read]** neatvnc H.264 is hardware only. src/enc/h264 has ffmpeg-impl.c using h264_vaapi and requires a GBM buffer object (it asserts NVNC_BUFFER_GBM_BO), plus v4l2m2m-impl.c. Software frames are skipped for H.264. (https://raw.githubusercontent.com/any1/neatvnc/master/src/enc/h264/ffmpeg-impl.c and src/server.c)
  - Why it matters: H.264 is unsuitable. The h2200 and PXA255 have no video encoder, a CPU H.264 encode at 400 MHz is not realistic, and it also needs a DRM/GBM render node. Skip it.
- **[read]** neatvnc damage and rate handling. Its 'damage refinery' hashes 32x32 tiles with XXH3 compiled with XXH_VECTOR=XXH_SCALAR (pure C) over the damaged area, to drop tiles that did not really change. It is skipped when no connected client needs it (n_damage_clients == 0). Each client accumulates damage in client->damage between sent frames. Before sending it estimates bandwidth and uses Fence round-trip time. If inflight_bytes exceeds estimate*(33.3 ms + min_rtt) it drops the frame, and the damage stays accumulated for the next one. The comment in display.c is 'TODO: Run the refinery in a worker thread?'. (https://raw.githubusercontent.com/any1/neatvnc/master/src/display.c, src/damage-refinery.c and src/server.c (lines ~1180-1240))
  - Why it matters: This gives automatic back-pressure for bt-pan if the viewer supports Fence, with no extra code in picowl. Scalar XXH3 on ARMv5 is a modest cost (see the estimate), but if picowl already supplies exact damage the refinery is duplicate work and could be made optional.
- **[read]** neatvnc takes frames in any DRM fourcc it supports and converts them per pixel to the client's pixel format (src/pixels.c, generic shift and mask recipe for 1, 2, 3 and 4 byte source and destination). So an RGB565 source and a 16 bpp or 8 bpp client format are possible. Whether RGB565 is in its supported-format table I did not confirm, because it comes from an X-macro table. (https://raw.githubusercontent.com/any1/neatvnc/master/src/pixels.c)
  - Why it matters: picowl's default render format is RGB565. A direct RGB565 to client 16 bpp path would avoid the generic conversion, which is a per-pixel cost on a CPU with no SIMD.
- **[read]** libvncserver (LibVNC) server supports Raw, CopyRect, RRE, CoRRE, Hextile, Zlib, Tight, Ultra, ZRLE, ZYWRLE and TightPNG (-260), and TRLE on the server side only. Its ZRLE uses deflateInit(Z_DEFAULT_COMPRESSION), which is level 6, with Z_SYNC_FLUSH. Its ZRLE template supports BPP 8, 16 and 32. ZYWRLE is compiled for BPP != 8 only. The ZYWRLE level is derived from the Tight quality level (quality <0 gives 1; <3 gives 3; <6 gives 2; else 1). The README suggests 16-bit or a palette colour mode for embedded use. (https://raw.githubusercontent.com/LibVNC/libvncserver/master/src/libvncserver/zrle.c, https://raw.githubusercontent.com/LibVNC/libvncserver/master/src/libvncserver/zrleoutstream.c and https://github.com/LibVNC/libvncserver/blob/master/README.md)
  - Why it matters: If the choice were libvncserver instead of neatvnc, it has Hextile and ZYWRLE, which neatvnc lacks, but its default zlib level is 6 and would be much slower on a 400 MHz CPU. It would need patching down to level 1. It is not a Wayland-aware library (no wlroots glue).
- **[read]** ZYWRLE (Hitachi Systems & Services, 2006, BSD-style licence) is ZRLE with a reversible Haar-like integer wavelet transform (reference cited: Senecal et al. 'N-bit to N-bit reversible Haar-like transform') plus quantisation, ahead of ZRLE. The libvncserver source (zywrletemplate.c) has no float or double (grep count 0). The authors report, for motion pictures, traffic of 15 to 50% of ZRLE; ZRLE compresses to about 30%, ZYWRLE to about 15% (hi quality) or 5% (mid quality). Those are the author's numbers, for natural video, on desktop PCs, and I did not find the original paper itself. (https://raw.githubusercontent.com/LibVNC/libvncserver/master/src/common/zywrletemplate.c (header and grep) and a search snippet quoting the ZYWRLE authors (the search results listed https://bugzilla.cendio.com/attachment.cgi?id=232 and the QEMU ui/vnc-enc-zywrle.h mirror; I could not open the QEMU mirror, which returned 404))
  - Why it matters: It is integer-only, so it is technically feasible on a PXA255 and it is the encoding designed for low bandwidth plus lossy video. Its added transform cost is not measured anywhere I found. It is ZRLE-based, so text gets blurry. Not useful for the crisp terminal, only for video.
- **[read]** Client support for ZYWRLE is narrow. libvncclient has it (rfbClientSetEncodings and rfbEncodingZYWRLE decoding). TigerVNC 1.16.2 (2026-03-26) has decoders for Raw, CopyRect, RRE, Hextile, Tight (with JPEG), ZRLE and H.264, and no ZYWRLE. noVNC's decoders are copyrect, h264, hextile, jpeg, raw, rre, tight, tightpng, zlib and zrle, also no ZYWRLE. UltraVNC was said to plan to adopt it, status unconfirmed. RealVNC, macOS Screen Sharing and the iOS apps: ZYWRLE support [unknown]. (https://api.github.com/repos/TigerVNC/tigervnc/git/trees/master?recursive=1 (common/rfb/*Decoder.cxx listing), https://api.github.com/repos/novnc/noVNC/git/trees/master?recursive=1 (core/decoders), https://raw.githubusercontent.com/LibVNC/libvncserver/master/src/libvncclient/rfbclient.c)
  - Why it matters: A ZYWRLE-only server would shut out most Mac/iOS clients. The viable common denominator across TigerVNC, noVNC, and probably RealVNC, Apple Screen Sharing and iOS apps is Raw, ZRLE and Tight (neatvnc offers exactly these).
- **[unknown]** zlib cost data is thin. The one number I found for a small ARM is a secondhand search snippet: 'gzip -1 compression throughput on Raspberry Pi: 1.87 MB/s' (Raspberry Pi 1 class ARM1176, 700 MHz presumably) from a ResearchGate figure 'Raspberry Pi Local Compression/Decompression Throughput'. The page returned 403, so I could not check the model, clock, file type or paper. It is not reliable. (https://www.researchgate.net/figure/Raspberry-Pi-Local-Compression-Decompression-Throughput_fig19_243962643 (403, not opened))
  - Why it matters: It is the only anchor for the zlib estimates below, so treat every CPU figure here as an order of magnitude (+-3x). Measuring zlib -1 and the neatvnc zrle-bench (bench/zrle-bench.c exists in the neatvnc repo) on the real h2200 is the way to settle it.
- **[read]** No published measurement found for PXA255, XScale, ARM9 or ARM926 for zlib, JPEG, ZRLE or Hextile. I searched for each. The only JPEG data surfaced was Linaro's 12-megapixel libjpeg-turbo decode on a Cortex-A9 OMAP4 (2078 ms without NEON, 1676 ms with), which is the wrong CPU and the wrong direction. Memory bandwidth reference for the ARM1176 (Raspberry Pi 1, 700 MHz): memcpy 387.6 MB/s, memset 1458.5 MB/s (tinymembench). (https://github.com/ssvb/tinymembench/wiki/Raspberry-Pi-(BCM2835) and https://www.cnx-software.com/2011/09/13/faster-jpeg-decoding-on-arm-with-libjpeg-turbo/)
  - Why it matters: All numbers in the cost table below are my extrapolations, not measurements.
- **[read]** TurboVNC/TigerVNC relative measurements (x86, 20 RFB session captures, data given relative to a baseline). In TigerVNC 1.1, zlib compression level 6 on top of Tight+JPEG took on average 56% more CPU than level 3 for only 4.3% more compression, and level 9 raised average CPU by a factor of 4.4 versus level 6 while compression got slightly worse. TurboVNC always uses zlib level 1 with JPEG. After the fixes in TigerVNC 1.2, compression levels above 2 gave 'virtually no gains'. TightVNC level 5 to level 9: CPU x5 for paltry gains. A TurboVNC mode with zlib level 7 and palette threshold 256 saves 10 to 20% bandwidth at nearly double the CPU on low-colour workloads. (https://turbovnc.org/pmwiki/uploads/About/turbototiger.pdf (VirtualGL Project, v1d 2012-03-09, pages 1 to 6 read) and the search snippet from the related 'From Tight to Turbo' report)
  - Why it matters: The lesson carries over to a weak CPU. Use zlib level 1 (neatvnc already does), do not raise levels, and do not use libvncserver's default of 6. Palette and solid-rectangle detection before zlib gives most of the saving. Zlib time grows far faster than the ratio improves.
- **[inf]** ESTIMATE, full-frame cost on a PXA255 at 400 MHz (assumes a full 240x320 redraw; typical updates are much smaller). Scaling assumptions: the XScale core is about 0.5 to 0.6 of an ARM1176 at 700 MHz in integer work per second (400 MHz at roughly 1.0 to 1.3 DMIPS/MHz against 700 MHz at roughly 1.25), and the 32 KB D-cache plus the slow SDRAM bus hurt zlib's 32 KB window and hash tables, so I took 0.4 to 0.5 of the Pi's 1.87 MB/s for zlib level 1, which is about 0.8 to 1.0 MB/s of input. Results: (a) Raw 16 bpp: no CPU, 153.6 KB on the wire. (b) zlib level 1 over 153.6 KB of raw RGB565: about 0.15 to 0.3 s, ratio unknown and content-dependent. (c) ZRLE of a terminal or bar frame (few colours, so the 16-entry palette and RLE reduce the data before deflate): per-pixel palette search plus format conversion at about 20 to 60 cycles per pixel, which is 76,800 px x 40 cycles = 3 Mcycles, about 8 ms, plus conversion and a small deflate, so roughly 10 to 40 ms per full frame. (d) ZRLE of a video frame (more than 16 colours per tile, so tiles are raw CPIXEL): conversion plus deflate over about 153 KB, roughly 0.2 to 0.4 s, with weak compression. (e) Hextile (not in neatvnc, would have to be written): one pass over pixels at about 10 to 30 cycles per pixel, so roughly 2 to 6 ms, no zlib, larger output than ZRLE. (f) Tight+JPEG with libjpeg-turbo's C path (no NEON/SIMD on ARMv5; integer DCT, TJFLAG_FASTDCT): assumed 100 to 300 cycles per pixel, so roughly 20 to 60 ms per full frame, with the large caveat that the cycles-per-pixel figure is a guess from general libjpeg experience. (g) ZYWRLE: ZRLE plus an integer wavelet transform, unmeasured, guess a transform of 30 to 80 cycles per pixel on top of ZRLE. (Derived from https://github.com/ssvb/tinymembench/wiki/Raspberry-Pi-(BCM2835), the unverified 1.87 MB/s snippet, and the neatvnc source structure (per-pixel memcmp palette, level 1 deflate). No measurement on ARMv5.)
  - Why it matters: Conclusion: CPU is not the dominant cost for UI content with ZRLE (tens of ms per full frame, a few ms for a line), whereas bandwidth is (see next finding). For video the CPU (hundreds of ms per full frame) and the link both fail, so video needs rate limiting rather than a better encoder.
- **[inf]** ESTIMATE, bytes on the wire at 240x320. Terminal or status bar with crisp fonts and an exact palette (picowl's crisp style) is two to a handful of colours per tile: ZRLE likely reaches roughly 10:1 to 30:1 against raw RGB565 (about 5 to 15 KB for a full redraw, under 1 KB for one changed text line of 240x16). Video or photo content: lossless ZRLE or Tight gives perhaps 1.2:1 to 3:1; Tight+JPEG at medium quality on 4:2:0 gives a guess of 5 to 15 KB per full frame, while text through JPEG looks bad and is bigger than palette coding. At 25 to 80 KB/s, a 5 to 15 KB frame is 0.06 to 0.6 s, so a few frames per second at best for video, and that is before encode time. (Reasoning from the RFB encoding definitions (tile palette and RLE) and the ZYWRLE authors' ZRLE 30% remark. No measurement on this content.)
  - Why it matters: For the terminal and panel, a damage-driven ZRLE update of the changed text rows makes bt-pan usable (sub-second). For the media player the sensible policy is to cap the update rate (for example 1 to 3 fps) or lower JPEG quality and subsampling, rather than try to follow the video.
- **[read]** Colour-depth reduction on the remote link. The client picks the format with SetPixelFormat (spec: 'the server must always be able to supply pixel data in the form the client wants'). Options: 16 bpp RGB565 (the same as picowl's buffer, so no conversion is needed if the server special-cases it), 8 bpp true-colour BGR233 (lossy, halves raw size, and the ZRLE CPIXEL becomes 1 byte), or a colour map (true-colour-flag 0) driven by SetColourMapEntries. libvncserver's ZYWRLE is not built for 8 bpp. neatvnc converts per pixel to whatever the client asks. The server cannot force the client's choice, so the viewer has to ask for it (for example a TigerVNC 'Color level' setting, or a libvncclient or custom client option). (https://raw.githubusercontent.com/rfbproto/rfbproto/master/rfbproto.rst (SetPixelFormat) and https://raw.githubusercontent.com/any1/neatvnc/master/src/pixels.c)
  - Why it matters: 16 bpp is the sensible default (matches the h2200 framebuffer, half of the 32 bpp wire size, no visible loss for UI). 8 bpp helps raw and zlib-light paths but ruins video and anti-aliased text. With ZRLE and a crisp palette the gain from 8 bpp is small, since palette tiles are already about 1 byte per pixel before RLE.
- **[read]** Cursor, DesktopSize and the other pseudo-encodings. Cursor (-239) or Cursor-with-alpha: the shape is sent once and the viewer draws it, so it is not in the frame. That is correct for picowl (a stylus has no hover-cursor anyway, and the pointer can be hidden). DesktopSize or ExtendedDesktopSize signals a rotation of 90 or 270 degrees, which picowl supports. QEMU Extended Key Event sends hardware keycodes so keyboard layouts are not confused (useful for the virtual keyboard path). Extended Clipboard has MIME-type and compressed text transfer. Fence synchronises and measures round-trip. neatvnc implements all of these. (https://raw.githubusercontent.com/rfbproto/rfbproto/master/rfbproto.rst and https://raw.githubusercontent.com/any1/neatvnc/master/src/server.c)
  - Why it matters: They cost the h2200 almost nothing and they remove traffic (cursor) or give pacing (Fence, ContinuousUpdates). They are cheap to enable once a server library handles them.
- **[inf]** Damage-driven updates change the picture the most. RFB is naturally damage-driven: a server only sends rectangles that changed since the client's last update, and with neatvnc picowl would give a frame plus a pixman damage region per commit. Because wlroots and picowl already compute damage for the MediaQ upload, the encoder cost scales with damaged pixels, not 76,800 px. A one-text-line change is about 3,840 px (240x16), so about 0.2 to 1 ms of conversion and palette work and a tiny deflate, a factor of 20 below the full-frame figures. Slow links merge damage between updates (neatvnc drops a frame when inflight bytes exceed the estimate and keeps the damage), so a busy source degrades to lower frame rate and not to lag. (Derived from https://raw.githubusercontent.com/any1/neatvnc/master/src/server.c and src/display.c plus the RFB incremental-update rules.)
  - Why it matters: This is why a low-CPU design is possible. The stance for picowl is: give neatvnc the exact damage from the compositor, do not add the XXH3 refinery (or make it optional), and cap max rectangle size for the video window.
- **[inf]** What compresses well. Terminal text in a crisp (non-anti-aliased) font: 2 colours per tile, so ZRLE or Tight palette give big ratios and RLE is cheap. A status bar: solid or a few colours, so Fill or solid-tile paths. A video player: noisy and full motion, so lossless coding barely helps and it needs JPEG (Tight) or ZYWRLE-type lossy coding, or rate limiting. Scrolling in a terminal would suit CopyRect, but neither neatvnc (selects no CopyRect) nor wlroots passes scroll hints, so each scroll is re-sent as changed pixels, which ZRLE handles because the data is mostly background. (Reasoning from the encoding definitions in https://raw.githubusercontent.com/rfbproto/rfbproto/master/rfbproto.rst and neatvnc's encoder selection in src/server.c)
  - Why it matters: This sets expectations per window. The two apps people actually use remotely (havoc and the panel) are the cheap cases, and the video player is the expensive one.
- **[inf]** Known to build or run without FPU on ARMv5: zlib (plain C), libjpeg and libjpeg-turbo (C path, integer DCT), pixman (already used by picowl), the neatvnc ZRLE and Tight encoders (integer only, no SIMD, from reading the source), and libvncserver ZRLE and ZYWRLE (integer only, from reading the source). Not established by anyone I could find: an actual run of neatvnc or libvncserver on an ARMv5/PXA device, neatvnc's aml dependency on that userland, and gnutls/nettle cost if TLS is enabled (TLS is probably off on bt-pan and USB). (Source reading as above. No project documents ARMv5 runs.)
  - Why it matters: Nothing in the encoders needs FPU, but nobody has published a PXA run, so a smoke test on the real device is the first step. TLS handshakes and per-byte crypto would add a lot of CPU, so prefer SSH tunnel or a trusted-link-only listener.

## Sweep 3: Link budget for remote access to an iPAQ h2200 (bt-pan, USB gadget, hx4700 Wi-Fi) and what a 240x320 remote screen costs

- **[read]** The h2200 series has integrated Bluetooth specified as v1.1, Class II (up to 4 dBm, typical 10 m range). It is a Bluetooth 1.1 radio, so there is no EDR and no 1.2 AFH. (https://hp.com/ctg/Manual/c00046403.pdf (HP h2200 QuickSpecs; text extracted locally: 'Integrated Bluetooth (v 1.1)', 'Class II device; up to 4 dBm transmit, typical 10 meter range'))
  - Why it matters: Fixes the radio class for the budget: use the Bluetooth 1.1 numbers (1 Mbit/s GFSK, DH5 ceiling about 723 kbit/s), not EDR. EDR only matters for a peer or later device.
- **[read]** A review of the h2215 says the h2200 uses a 'Zeevo system-on-chip Bluetooth'. Zeevo's ZV4002 was marketed as a single-chip ARM7 Bluetooth SoC, and Zeevo later announced a Bluetooth 1.2 single-chip part. I did not find which Zeevo part is in the h2200, how it is attached (UART or other) or at what baud rate. (https://www.pencomputing.com/frames/hp_ipaq_2215.html ; Zeevo ZV4002 and 1.2 announcement only seen as search-result snippets (eetimes.com/?p=1179823, electronicdesign.com/embedded/highly-integrated-bluetooth-ic-simplifies-design))
  - Why it matters: The chip is known (Zeevo), the host link and UART speed are not. Zeevo parts are not in BlueZ hciattach's chip list, which has bcsp, csr, swave, texas, etc. (see next finding). Check the h2200 kernel/OE tree for how the h2200 attaches it.
- **[read]** Upstream BlueZ hciattach.c has no 'zeevo' type. Types seen include bcsp, csr, swave, texas (HCILL), with defaults of 115200 baud initial speed. The Linux H4 UART line discipline and hci_uart stack are the generic way to attach a UART Bluetooth controller. (https://raw.githubusercontent.com/bluez/bluez/master/tools/hciattach.c (grep done locally, 2026))
  - Why it matters: On the h2200 the Zeevo part probably attaches via a generic H4/'any' type or a vendor init script. This is [inf]. Whether the Zeevo part's UART is clocked above 115200 under Linux is unknown, and it is the single biggest unknown in the bt-pan budget.
- **[read]** The handhelds.org wiki and git pages are no longer served. The domain now redirects to an unrelated site (hoverwatch.com), so the original h2200 Linux Bluetooth documentation could not be read. OpenEmbedded's h2200 machine config lists the features 'bluetooth irda usbgadget pcmcia' and a serial console on ttyS0 at 115200. (https://git.openembedded.org/openembedded/tree/conf/machine/h2200.conf)
  - Why it matters: No primary source for the BT UART speed. This is the highest-value thing to measure on the device (stty -F on the BT tty, hciconfig -a, or the BT driver in the h2200 kernel).
- **[read]** Bluetooth 1.x ACL ceilings: DH5 carries 339 payload bytes in a 5-slot packet plus 1 return slot (6 x 625 us = 3.75 ms), which gives 339*8/3.75 ms = 723.2 kbit/s (90.4 KB/s) asymmetric. DM5 carries 224 bytes, which gives 477.8 kbit/s (59.7 KB/s). Symmetric DH5 gives 433.9 kbit/s (54.2 KB/s). Raw radio rate is 1 Mbit/s. (Wikipedia https://en.wikipedia.org/wiki/Bluetooth (1 Mbit/s, v1.2 'up to 721 kbit/s'); electronics-notes https://www.electronics-notes.com/articles/connectivity/bluetooth/data-file-transfer.php (433.9 symmetric, 'up to 732.2' sic); DH5/DM5 byte counts from a search-result summary. The 723.2/477.8 arithmetic is mine and agrees with the cited figures.)
  - Why it matters: These are the physical ceilings before L2CAP, BNEP, IP and TCP overhead, retransmissions and host limits. Everything measured in PDAs is far below them.
- **[read]** EDR (Bluetooth 2.0+EDR): 3 Mbit/s raw, 2.1 Mbit/s maximum data rate after inter-packet time and acknowledgements. 2-DH5 carries up to 681 bytes and 3-DH5 up to 1023 bytes per packet. (https://en.wikipedia.org/wiki/Bluetooth ; packet sizes from a Bluetooth patent summary at image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/8577291)
  - Why it matters: EDR could help a future device but not the 1.1 h2200. A link to a 2.0+EDR peer still runs at 1.1 speeds on this radio.
- **[read]** Measured BNEP/PAN over Bluetooth 1.1 CSR hardware on Linux, 2005 (LKML thread by Pavel Machek): Billionton CF card, UART HCI over BCSP at 921,600 baud, LMP 1.1, ACL MTU 192:8, 3-slot and 5-slot packets supported. A 1,000,000-byte TCP transfer took 103.18 s = 9.464 KB/s (about 76 kbit/s), 'about 10 KB/sec' typical. Ping was about 50-85 ms idle, climbing to 4-13 s during the transfer, with 'NETDEV WATCHDOG: bnep0: transmit timed out'. A USB dongle gave about 25 KB/s with a Nokia 6230. Ed Tomlinson reported 'about the same' with a USB adapter. One log shows a USB disconnect before the failures, so some of the result may be hardware or driver trouble. (https://lkml.indiana.edu/0510.2/1461.html ; https://lkml.iu.edu/hypermail/linux/kernel/0510.2/1514.html ; https://lkml.iu.edu/hypermail/linux/kernel/0510.2/1486.html)
  - Why it matters: The best hard datum for BNEP on 1.1-class hardware: 10-25 KB/s (80-200 kbit/s) goodput, and latency that explodes under load (bufferbloat in the HCI/L2CAP queues). Here a 0.5 s frame upload would delay the next keystroke by seconds unless the sender paces itself. It argues for small updates and a rate cap.
- **[unknown]** A search snippet claims about 80 KB/s for Linux-to-Linux BlueZ PAN and typical ping of 40-75 ms on the orbit-lab Bluetooth HowTo. I could not read the page (it moved to cosmos-lab.org and the statement was not found), so it is unverified. (https://orbit-lab.org/wiki/HowTo/Bluetooth/UsingCL?version=5 (not confirmed))
  - Why it matters: Do not rely on 80 KB/s. It would be about 88% of the DH5 ceiling, which is implausible for a PDA with a 115200-921600 baud UART.
- **[inf]** UART arithmetic. A UART at 115,200 baud 8N1 moves at most 11,520 B/s. At 230,400 it is 23,040 B/s, at 460,800 it is 46,080 B/s and at 921,600 it is 92,160 B/s. The H4 framing adds a 1-byte type and 4-byte ACL header per packet. PXA255 standard UARTs derive baud from a 14.7456 MHz clock (max 921,600), which is from my memory and unchecked. (arithmetic; PXA255 UART clock from memory, not verified at a URL)
  - Why it matters: If the h2200 BT UART stays at 115,200 baud the whole link tops out near 11 KB/s even if the air could do 90 KB/s. That matches the 9.5-10 KB/s LKML numbers and is the likely worst case for the h2200. If it is 921,600 the air interface is the limit instead.
- **[read]** A BNEP frame is carried in L2CAP. The BNEP MTU is 1691 bytes (1500-byte payload plus headers). A UCL paper computes 1691*8/115,200 = 117 ms to push one full-MTU BNEP frame through a 115,200-baud UART. (https://www.ee.ucl.ac.uk/lcs/previous/LCS2005/67.pdf (Yang & Pollard, 'Routing in Bluetooth Personal Area Networks', 2005; text via pdftotext))
  - Why it matters: On a 115,200-baud UART a single full-size packet blocks the link for 117 ms. Keep the BNEP/IP MTU small for interactivity (for example 576 or less, at most 1 packet in flight) so a keystroke does not queue behind a large update.
- **[read]** The Linux gadget code gives the theoretical bulk peak on a full-speed link as gether_bitrate = 19 * 64 * 1 * 1000 * 8 = 9,728,000 bit/s (19 bulk packets of 64 bytes per 1 ms frame), i.e. 1.216 MB/s. (https://raw.githubusercontent.com/torvalds/linux/master/drivers/usb/gadget/function/u_ether.h)
  - Why it matters: Upper bound for usb0 at USB 1.1 full speed. Real throughput on the PXA255 will be lower (see next findings).
- **[read]** pxa25x_udc is the PXA25x USB 1.1 full-speed device controller. It has 15 fixed endpoints, a 64-byte bulk FIFO and 16-byte ep0. The driver does NOT use DMA: IN-DMA needs 16-byte aligned data, which the network stack does not provide, and OUT-DMA is 'buggy in most chip versions', so the transfers are PIO by the CPU. The driver sets quirk_altset_not_supp = 1 and only supports SET_INTERFACE for the default altsetting. (https://raw.githubusercontent.com/torvalds/linux/master/drivers/usb/gadget/udc/pxa25x_udc.c (header comment and line ~1373); https://raw.githubusercontent.com/torvalds/linux/master/drivers/usb/gadget/udc/pxa25x_udc.h (BULK_FIFO_SIZE 64))
  - Why it matters: USB gadget networking on the h2200 is PIO-bound on a 400 MHz CPU and costs CPU cycles per byte. This is a CPU-load issue as well as a bandwidth one.
- **[read]** Because pxa25x_udc reports altsettings as unsupported, the legacy g_ether gadget cannot use CDC ECM there (can_support_ecm() is false) and falls back to 'CDC Subset/SAFE' (vendor 0x049f/0x505a, ARM-Linux usb-eth style). RNDIS is still possible alongside it. g_ether also defines RNDIS and EEM variants. (https://raw.githubusercontent.com/torvalds/linux/master/drivers/usb/gadget/legacy/ether.c ; https://raw.githubusercontent.com/torvalds/linux/master/include/linux/usb/gadget.h (gadget_is_altset_supported) ; u_ether.h can_support_ecm)
  - Why it matters: The h2200 USB link will be CDC Subset (Linux host driver cdc_subset, no other OS ships one) or RNDIS (Windows and Linux hosts, not macOS). I did not verify macOS driver support for either. From memory macOS has CDC ECM/NCM drivers but no RNDIS, so a Mac would need a Linux box or Windows machine in the path. [inf]. This matters because the user is on macOS.
- **[unknown]** No measured usb0 throughput for pxa25x/h2200 was found. One search snippet said RNDIS on full speed is 'typically in the order of 0.6 MB/s'. I could not trace it to a primary source. Wall-clock expectation from arithmetic: ~1.2 MB/s theoretical bulk peak minus RNDIS/Ethernet/IP/TCP overhead and PIO cost is plausibly 0.3-0.8 MB/s. (search snippet only, not verified)
  - Why it matters: Treat as 300-600 KB/s [inf, unmeasured] for planning. It would be 30-60x the bt-pan 10 KB/s figure, so USB is the 'unconstrained' case for full-frame Raw.
- **[read]** iPAQ hx4700 Wi-Fi is 802.11b (11 Mbit/s raw). Linux support for it used an acx-family driver (hx4700_acx) with firmware files, working on 2.6.21+ kernels. No hx4700 Linux throughput number was found. Measured 802.11b PDA throughput of the era over SD-bus Wi-Fi was poor: HP H2210 + SanDisk SD Wi-Fi gave 0.4 Mbit/s (Chariot) and 0.3 Mbit/s (FTP); PalmOne Tungsten C (CF-style internal) 2.7 Mbit/s FTP; ASUS A716 1.0 Mbit/s FTP / 4.1 Mbit/s Chariot; Dell Axim X3 + SD Wi-Fi 0.4 Mbit/s FTP. The cause was the SD bus run in 1-bit mode at up to 20 MHz. All measurements were within about 6 feet of the access point, under WinCE. (https://www.smallnetbuilder.com/wireless/wireless-features/wifipdasecretntkpt1/ ; https://danballard.com/2007/11/07/making-familiar-0.8.4-linux-useful-on-the-ipaq-hx4700/ ; hx4700 802.11b from reviews at https://www.the-gadgeteer.com/review/hp_ipaq_hx4700_pocket_pc_review)
  - Why it matters: The hx4700 Wi-Fi is not the same attachment as those SD cards, so the numbers are only indicative. Plan 1-4 Mbit/s (125-500 KB/s) as realistic for 802.11b on a PXA27x, [inf], which is 10-50x bt-pan. hx4700 has 480x640, so a full frame is 4x larger (see arithmetic).
- **[inf]** Frame sizes for a 240x320 screen (76,800 pixels): Raw RGB565 = 76,800 x 2 = 153,600 B; 8-bit indexed = 76,800 B; packed RGB888 = 230,400 B; RFB 32 bits-per-pixel (what the protocol uses for 24-bit colour: bits-per-pixel must be 8, 16 or 32) = 307,200 B. The hx4700 480x640 is 307,200 pixels: 614,400 B in RGB565. RFB Raw adds only a 16-byte message+rectangle header (4-byte FramebufferUpdate header + 12-byte rectangle header). (arithmetic; RFB header/pixel-format facts [read] at https://www.rfc-editor.org/rfc/rfc6143.txt (FramebufferUpdate 4 B, rectangle header 12 B, bits-per-pixel 8/16/32, CPIXEL 3 bytes for ZRLE at depth<=24))
  - Why it matters: RGB565 raw is the natural wire format for picowl (same as the frame buffer, no conversion). RGB888 gains nothing on a RGB565 panel, and only ZRLE's 3-byte CPIXEL avoids the 4-byte penalty.
- **[inf]** Time to send one full 153,600 B RGB565 frame uncompressed: at 10 KB/s (measured BNEP, LKML) = 15.4 s; at 25 KB/s = 6.1 s; at 90.4 KB/s (the DH5 asymmetric ceiling, never reached) = 1.7 s; at 400 KB/s (guess for usb0) = 0.38 s; at 250 KB/s (guess for 802.11b) = 0.61 s. An 8-bit frame (76,800 B) halves those times: 7.7 s at 10 KB/s. So an uncompressed full frame is usable only on USB or Wi-Fi, never on bt-pan, even once. (arithmetic from the figures above)
  - Why it matters: On bt-pan the initial full-screen sync alone takes 6-15 s even before any updates. Compression (ZRLE/Tight-style, UI content compresses well) or a progressive/low-colour initial frame is essential.
- **[inf]** Terminal update sizes, assuming an 8x16-pixel character cell (30 columns x 20 rows on 240x320) and Raw RGB565 with a 4-byte message header and 12-byte rectangle header per rectangle: one cell = 128 px x 2 B = 256 B + 16 = 272 B. Typing one character normally changes two cells (the old cursor cell and the new character plus cursor) = 2*(12+256)+4 = 540 B. One full text line (240x16 = 3,840 px) = 7,680 B + 16 = 7,696 B. A full scroll of the 20-row terminal is a whole-screen update of ~153,600 B Raw, but a CopyRect (RFB, 16 bytes of payload) plus one new line = about 7.7 KB. (arithmetic (cell size is my assumption, not read from havoc's config); CopyRect and rectangle sizes from RFC 6143)
  - Why it matters: With 10 KB/s the 540 B echo update serialises in 54 ms, a full line in 770 ms, a CopyRect scroll plus a line in about 0.8 s. Using CopyRect for scroll and a damage-tight bounding box is mandatory. picowl would need to emit per-damage rectangles (it already tracks damage for the MediaQ commit).
- **[inf]** Compression estimates for a terminal line or cell (no measurement, depends on font): Hextile on a 2-colour glyph tile is roughly 1 mask byte + 2 B background + 2 B foreground + 1 B subrect count + 2 B per subrectangle, so about 25-45 B per 16x16 tile at 10-20 subrects. A 15-tile text line would be about 400-700 B (versus 7,696 B raw). ZRLE (zlib over 64x64 tiles, with a persistent zlib stream across updates) typically compresses a line of text to a few hundred bytes. Both are estimates. (encoding structure [read] at https://www.rfc-editor.org/rfc/rfc6143.txt; sizes are my estimates)
  - Why it matters: A 10-20x reduction makes a line cost about 40-70 ms at 10 KB/s rather than 770 ms. Encoder CPU on a PXA255 without FPU is unknown. zlib and Hextile are integer-only, so no FPU is needed, but no ARMv5 speed figure for zlib deflate was found. Measure it before choosing ZRLE over Hextile.
- **[inf]** Video, 240x136 = 32,640 px, per frame: Raw RGB565 = 65,280 B (10 fps = 653 KB/s = 5.2 Mbit/s; 25 fps = 1.63 MB/s = 13 Mbit/s); 8-bit = 32,640 B (10 fps = 326 KB/s; 25 fps = 816 KB/s); RFB 32-bit = 130,560 B (10 fps = 1.3 MB/s). Against the budgets: bt-pan at 10 KB/s allows 0.15 frame/s Raw565, 0.3 frame/s 8-bit. USB at 400 KB/s allows about 6 fps Raw565 or 12 fps 8-bit. Even the BT ceiling of 90.4 KB/s allows only 1.4 fps Raw565. (arithmetic)
  - Why it matters: Mirroring video over bt-pan with a generic pixel encoding is impossible. To carry 10 fps within 10 KB/s you need 1,000 B/frame = 0.25 bits/pixel (a 260:1 ratio over RGB565), and at 25 KB/s with 5 fps you need 5,000 B/frame = 1.2 bits/pixel. JPEG-class codecs reach roughly 1 bit/pixel at poor quality (my estimate), so about 1-3 fps of 'live' video is the bt-pan limit. A sensible policy is to drop to a low frame rate or pause the video region and send keyframes on request.
- **[inf]** Display-bus cost when mirroring locally versus remotely, from the task's own numbers: a full 153,600 B upload at 7.9-9.1 MB/s takes 16.9-19.4 ms with the CPU stalled. A 240x136 video region (65,280 B) takes 7.2-8.3 ms per frame, which is 18-21% CPU stall at 25 fps and 7-8% at 10 fps. (arithmetic: 153,600/9.1e6 = 16.9 ms, 153,600/7.9e6 = 19.4 ms; 65,280/9.1e6 = 7.2 ms, /7.9e6 = 8.3 ms)
  - Why it matters: This is what blanking the display during a session saves. It is a CPU-time win (10-20% at video rates), and nothing for bt-pan bandwidth, which the link caps long before. The saving is real only if the frame is read from RAM (shadow buffer), never read back from the MediaQ.
- **[read]** Interactive latency tolerance: Nielsen's 0.1 s is 'the limit for having the user feel that the system is reacting instantaneously', 1 s is 'the limit for the user's flow of thought to stay uninterrupted'. In the Mosh paper (MIT, 2012), over a Sprint EV-DO link median SSH keystroke response was 503 ms (mean 515 ms), versus Mosh with predictive local echo at a 5 ms median and 173 ms mean, which shows that local echo, not bandwidth, is how a high-RTT link feels responsive. (https://www.nngroup.com/articles/response-times-3-important-limits/ ; https://mosh.org/mosh-paper.pdf (Winstein & Balakrishnan, USENIX ATC 2012; read via pdftotext))
  - Why it matters: Budget: keyboard echo within about 100-200 ms feels fine, 0.5 s is tolerable for typing but annoying, and over 1 s breaks flow. A stylus drag needs below about 100 ms to feel direct. BT idle RTT of 40-85 ms (LKML) plus serialisation of a 540 B update at 10 KB/s (54 ms) gives about 100-140 ms for a typed character, which is just inside the limit if the link is not otherwise loaded and the sender never queues big updates ahead of small ones.
- **[inf]** Practical budget proposal for bt-pan (Bluetooth 1.1, assumed 10-25 KB/s goodput, 50-85 ms idle RTT): sustained average of at most about 5-8 KB/s of remote-screen payload (leave a share for ACKs, input events and other traffic), a pending-update cap of about 2-4 KB so latency stays under bufferbloat, frame-rate cap of about 2-5 fps for changes, with compressed encodings only (Hextile or ZRLE; Tight/JPEG for video regions). Use CopyRect for scrolls, 16-bit RGB565 (or an 8-bit palette for initial sync). Typing echo and cursor updates (about 300-600 B compressed) always get priority. Full-frame initial sync costs roughly 5-15 KB compressed (6-15 s for Raw is not acceptable), which is 1-3 s. These compressed sizes are estimates. (synthesis of the figures above)
  - Why it matters: Recommended design targets for the remote path. On USB (about 300-600 KB/s, unmeasured) and 802.11b (about 125-500 KB/s) nearly any encoding fits and Raw565 at 2-5 fps for video is possible; the CPU, not the link, becomes the limit, so use cheap encodings (Raw/CopyRect/Hextile) there.
- **[inf]** Per-packet overhead of the PAN path over Bluetooth: L2CAP header 4 B, BNEP 3 B (compressed Ethernet) up to 15 B, HCI ACL 4 B, UART H4 type byte, plus IP 20 B and TCP 20 B (and 12 B for timestamps) per segment. A small 540 B update therefore carries roughly 60-80 B of headers, about 10-15%. Pure ACKs add another about 50-60 B per direction. (header sizes from memory of the protocol specs, with BNEP 1691-byte MTU from the UCL paper above; not individually verified)
  - Why it matters: Matters for small keystroke updates (about 12%) but not for large ones. Set TCP_NODELAY on the RFB socket, as Nagle would add up to 200 ms of delay to echo.
- **[inf]** Known to work on 32-bit ARMv5 without an FPU: BlueZ (hci_uart, BNEP/pand) and pxa25x_udc with g_ether were used on PXA25x iPAQs and Zaurus in 2005-2007 (kernel 2.6.x). zlib, Hextile, CopyRect and libjpeg's integer DCT need no FPU. Not established: any measured encoder speed on a PXA255, any measured bt-pan or usb0 throughput on an h2200, and the h2200's Bluetooth UART speed. (kernel sources above; claim about PXA iPAQs using USB net from Kconfig/ether.c comments ('ARM Linux has used for ethernet-over-usb, both with sa1100 and with pxa250'))
  - Why it matters: Everything is feasible in principle. Priority device measurements: (1) BT UART baud and hciconfig features, (2) iperf/tcp throughput and ping under load on bnep0 and usb0, (3) encoder cost per KB on the PXA255 for zlib/Hextile.

## Sweep 4: Remote-access CLIENTS per option (VNC/RFB, RDP, Waypipe) for picowl on h2200 over bt-pan or USB; user on macOS/iOS first, Linux second

- **[read]** wayvnc README names three real authentication schemes: VeNCrypt (TLS, X509 key and cert, username/password), RSA-AES (RSA with AES-EAX, trust-on-first-use), and legacy DES VNC auth (no encryption). It also allows no authentication, with a warning against untrusted networks. (https://raw.githubusercontent.com/any1/wayvnc/master/README.md)
  - Why it matters: Shows what a server on the wlroots/Wayland side offers. No encryption is the realistic choice over a trusted USB link. On bt-pan each TLS or RSA-AES handshake costs CPU on a PXA255 with no FPU.
- **[read]** wayvnc says its DES auth option exists 'solely for compatibility with VNC clients that support DES but do not support the absence of authentication, such as macOS Screen Sharing'. So macOS Screen Sharing cannot connect to a security-type-None server, and needs VNC password (DES) or an Apple ARD type. (https://github.com/any1/wayvnc)
  - Why it matters: Decisive for a macOS-first user. A picowl server that offers only None will not work with the built-in Screen Sharing. It must offer VNC auth, or Apple DH (see next finding).
- **[read]** neatvnc (the library under wayvnc, ISC licence, version 1.1-dev) ships src/auth/apple-dh.c, which implements Apple's Diffie-Hellman ARD auth. It derives an MD5 of the shared secret as an AES-128-ECB key and decrypts a 64-byte username plus a 64-byte password. It also ships vencrypt.c, des-auth.c and rsa-aes.c. (https://raw.githubusercontent.com/any1/neatvnc/master/meson.build and https://raw.githubusercontent.com/any1/neatvnc/master/src/auth/apple-dh.c)
  - Why it matters: A neatvnc-based server can accept macOS Screen Sharing logins with username/password. Whether Screen Sharing actually completes the handshake against neatvnc is not shown in anything I read, so it is not tested.
- **[read]** neatvnc's server.c on_client_set_encodings accepts these encodings: Raw, CopyRect, RRE, Hextile, Tight, TRLE, ZRLE, Open H.264. It also accepts the pseudo-encodings Cursor, DesktopSize, ExtendedDesktopSize, DesktopName, QEMU ext key, LED state, extended clipboard, ContinuousUpdates, ExtMouseButtons, Fence and JPEG quality levels. Frame encoding choice: Raw, Tight or ZRLE if the client asked for them; H.264 only for GBM buffers when a working encoder exists; otherwise Raw. This is from a model-summarised fetch of the source, not a direct reading of the file. (https://raw.githubusercontent.com/any1/neatvnc/master/src/server.c)
  - Why it matters: If picowl reuses neatvnc, H.264 is effectively out (no GBM, no hardware encoder, no GPU). The CPU encoders are ZRLE or Tight (Tight JPEG needs libturbojpeg, optional). neatvnc also has parallel-deflate.c and damage-refinery.c, which target multi-core hosts, so the PXA255 gets no benefit from them.
- **[read]** neatvnc's hard dependencies are pixman, zlib, aml and libdrm. Optional ones are libturbojpeg, gnutls, nettle/hogweed/gmp, gbm, ffmpeg libs, libpng and libsixel. It takes frames as DRM/GBM or plain buffers and has no Wayland-version restriction in the files I read. (https://raw.githubusercontent.com/any1/neatvnc/master/meson.build)
  - Why it matters: pixman and zlib are already in picowl's world. A build without gnutls, nettle, ffmpeg and gbm is plausible. Whether it has ever been built or run on armv5e soft-float is [unknown]. I found no report of it.
- **[read]** TigerVNC vncviewer encodings: Tight, JPEG, ZRLE, Hextile, H.264 and Raw. Options: PreferredEncoding, CompressLevel (0-9, default 2), QualityLevel (0-9, default 8), NoJPEG, LowColorLevel/FullColor (reduced colour for slow links), AutoSelect (default on). Security types: None, VncAuth, Plain, TLSNone/TLSVnc/TLSPlain, X509*, RA2, RA2ne, RA2_256, RA2ne_256. Licence is GPL, with builds for Windows, Linux and macOS (FLTK viewer). (https://tigervnc.org/doc/vncviewer.html and https://github.com/TigerVNC/tigervnc/blob/master/README.rst)
  - Why it matters: Best-documented tuning knobs for a slow link: LowColorLevel plus ZRLE or Tight at a low QualityLevel. It runs on macOS and Linux, but it is a desktop app and is not on iOS. It does not support Apple ARD auth, so against a Screen-Sharing-style server it needs VncAuth, VeNCrypt or RA2.
- **[read]** macOS built-in Screen Sharing: a secondary search result states it supports only Zlib and ZRLE encodings, uses ARD security type 30 (undocumented in the RFC), and limits classic VNC passwords to 8 characters. Some clients (tightVNC) cannot connect to Screen Sharing as a server, while RealVNC can. These are third-party summaries (HackTricks and similar), not Apple documentation. (https://book.hacktricks.xyz/macos-hardening/macos-security-and-privilege-escalation/macos-protocols)
  - Why it matters: If it is right, the server must offer ZRLE (no Tight, no H.264). ZRLE ignores JPEG quality, so it cannot be tuned lossy. Reduced colour depth and a small framebuffer are the only levers. The claim that Screen Sharing sends only Zlib/ZRLE is the server-side view of Apple's own server, and I did not verify the viewer's encoding list directly.
- **[unknown]** The viewer in Screen Sharing.app (open vnc://host) is a plain macOS app with no quality, colour-depth or compression controls that I could find documented. Its viewer-side encoding list and pseudo-encoding support (cursor, desktop resize, continuous updates) could not be established from a primary source.
  - Why it matters: For bt-pan the user cannot tune the built-in viewer. If the first connection is slow, a server-side colour reduction or a smaller framebuffer is the only lever. Treat Screen Sharing as 'works if the server matches', not as the slow-link client.
- **[read]** noVNC (browser, MIT-style, runs on macOS, iOS Safari 15+ and Android): encodings raw, copyrect, rre, hextile, tight, tightPNG, ZRLE, JPEG, Zlib, H.264. Auth: none, classic VNC, RSA-AES, Tight, VeNCrypt Plain, XVP, Apple DH, UltraVNC MSLogonII. It needs WebSocket on the server, or the websockify proxy. Settings: quality 0-9, compression 0-9, resize off/scale/remote, view_clip. It has local cursor rendering and touch gestures. (https://github.com/novnc/noVNC/blob/master/README.md and https://github.com/novnc/noVNC/blob/master/docs/EMBEDDING.md)
  - Why it matters: The one client that works identically on macOS, iOS and Linux with no install, and it supports Apple DH. Its WebSocket requirement matters: neatvnc ships src/stream/ws/ (WebSocket), so wayvnc/neatvnc can serve noVNC directly. Colour depth is not a setting in noVNC. Compression and quality are. Running websockify on a peer machine would cost nothing on the h2200 and would only add a hop.
- **[read]** LibVNCServer (GPLv2) server encodings: Raw, CopyRect, RRE, CoRRE, Hextile, Zlib, Tight, Ultra, ZRLE, ZYWRLE, TightPNG. Server auth: VNC auth and None only. Client side adds SASL, TLS, VeNCrypt and Apple ARD. Its docs recommend lossy encodings, reduced colour depth or a scaled-down framebuffer for slow connections. WebSockets are supported. (https://raw.githubusercontent.com/LibVNC/libvncserver/master/README.md)
  - Why it matters: A mature small-footprint server with plain VNC auth, which macOS Screen Sharing accepts. ZYWRLE (wavelet-lossy ZRLE) is supported by the server and by libvncclient, but which viewers send ZYWRLE is [unknown] from what I read (TigerVNC and the macOS viewer do not list it). GPL linking affects the picowl licence.
- **[read]** Jump Desktop (iOS/macOS/Android, commercial): a search-result snippet lists VNC encodings copyrect, zrle, tight, (zlib)hextile, zlib, rre, raw and desktop-resize. ## Sweep 5: Remote access (VNC/RFB) for picowl with a remote-only mode (no local display upload) on the iPAQ h2200 over bt-pan/usb0: integration, wlroots 0.19 support, clients, design proposal

- **[read]** PROVENANCE. I read the picowl repo and the checked-out wlroots 0.19.0 tree (commit 13a62a23, with picowl's patches applied as uncommitted changes) read-only. gitlab.freedesktop.org/wlroots returned an Anubis 403 to WebFetch, so every wlroots claim below comes from the local tree, not the web. wayvnc/neatvnc sources were read from raw.githubusercontent.com master (wayvnc version 0.11-dev; releases up to v0.10.2 dated 2026-09-25 per the GitHub API). Nothing was built, run or measured on an armv5e device. (/Users/koen/Projects/Angstrom/Tiny-UI-research/picowl/subprojects/wlroots ; https://raw.githubusercontent.com/any1/wayvnc/master/meson.build ; https://api.github.com/repos/any1/wayvnc/releases)
  - Why it matters: Sets the confidence level: all behaviour claims are from source reading, none from running on the h2200.
- **[read]** CAPTURE TODAY (what the buffer is). wlroots 0.19 wlr_screencopy_v1 does not re-render. It listens to the output 'commit' event and, when the commit has WLR_OUTPUT_STATE_BUFFER, reads event->state->buffer, the very buffer that was just committed to the output: frame_handle_output_commit -> frame_shm_copy -> wlr_texture_from_buffer(renderer, src_buffer) + wlr_texture_read_pixels into the client's wl_shm buffer. With the pixman renderer that is one CPU RAM-to-RAM copy of the requested box, done synchronously inside the compositor's commit handler. It never reads video memory: on mq11xx the committed buffer is the system-RAM shadow plane (picowl's single-slot copy_swapchain), and the kernel driver copies damage clips from it to the MediaQ. (/Users/koen/Projects/Angstrom/Tiny-UI-research/picowl/subprojects/wlroots/types/wlr_screencopy_v1.c (lines 193-344); /Users/koen/Projects/Angstrom/Tiny-UI-research/picowl/doc/zero-copy.md (table: mq11xx 'shmem shadow plane', caching cacheable))
  - Why it matters: Answers 'RAM or video memory, how many copies': the capture already reads RAM. Cost is 1 composition (already needed for the display) + 1 memcpy-class copy of the frame/box into the shm buffer, regardless of the display.
- **[read]** A screencopy request forces a frame and defeats direct scanout while pending. frame_handle_copy calls wlr_output_update_needs_frame() and wlr_output_lock_attach_render(output,true) (and wlr_output_lock_software_cursors when overlay_cursor is set). wlr_output_is_direct_scanout_allowed() returns false while attach_render_locks > 0. copy_with_damage frames (what wayvnc uses) do not complete on a commit with empty damage, so an idle screen costs no capture work. (/Users/koen/Projects/Angstrom/Tiny-UI-research/picowl/subprojects/wlroots/types/wlr_screencopy_v1.c (lines 283-447); types/output/output.c line 966; https://raw.githubusercontent.com/any1/wayvnc/master/src/screencopy.c)
  - Why it matters: During a remote session zero-copy/direct-scanout clients (player Path A) are composited once per captured frame. An idle session costs nothing because wayvnc uses copy_with_damage.
- **[read]** A DISABLED OUTPUT CANNOT BE CAPTURED. screencopy sends failed() if !output->enabled at copy time and on any commit that disables it (frame_handle_copy, frame_handle_output_commit). picowl's blank (power key, dim.c BLANKED, zwlr_output_power OFF) does output_commit_disable() on every DRM output (output_set_power in output.c), after which no frame event fires, nothing is rendered and the copy_swapchain is destroyed. So today blanking and capture are mutually exclusive: the compositor does NOT keep rendering when blanked. (/Users/koen/Projects/Angstrom/Tiny-UI-research/picowl/src/output.c (output_set_power, pw_output_blank); /Users/koen/Projects/Angstrom/Tiny-UI-research/picowl/subprojects/wlroots/types/wlr_screencopy_v1.c lines 290-292, 364-368)
  - Why it matters: Central fact for the design: 'screen off' as implemented today stops rendering as well, so a remote viewer needs a separate render target that stays enabled.
- **[read]** FRAME FLOW today. output_frame() in output.c calls wlr_scene_output_commit() only when the scene has damage (or needs_frame), passing the picowl-owned one-slot copy_swapchain on copy-type outputs. wlroots renders (pixman) the damaged region into that RGB565 buffer in RAM and commits it with the damage region; the patched DRM backend passes FB_DAMAGE_CLIPS and the mq11xx driver copies those rectangles to the 256 KiB VRAM during the commit; at page flip the fb is released (drm_fb_clear) so the one slot is reusable. Small rectangles are filled by the 2D engine instead of uploaded. A full frame is 153,600 bytes (about 17.5 ms of bus). (/Users/koen/Projects/Angstrom/Tiny-UI-research/picowl/src/output.c (output_frame, copy_swapchain_create); /Users/koen/Projects/Angstrom/Tiny-UI-research/picowl/doc/zero-copy.md; /Users/koen/Projects/Angstrom/Tiny-UI-research/picowl/doc/rotation-results.md; /Users/koen/Projects/Angstrom/Tiny-UI-research/picowl/subprojects/wlroots/backend/drm/drm.c (copy_type handling))
  - Why it matters: Shows exactly what remote-only must skip: the KMS commit with damage clips (the VRAM upload). Composition (pixman into RAM) is separate and stays.

- **[read]** RFB PROTOCOL FACTS (RFC 6143): only Raw is mandatory for clients; CopyRect, RRE, Hextile, TRLE, ZRLE are optional ('current servers use ZRLE, TRLE and CopyRect'); the client chooses the pixel format with SetPixelFormat (8, 16 or 32 bpp); updates are demand-driven (an update is sent only in response to a FramebufferUpdateRequest). ## Skeptic's review

**Skeptic review of the four remote-access sweeps (VNC/RFB for picowl on the h2200)**

Checked by fetching the sources and by reading the local wlroots tree. Anything I did not open is marked UNCHECKED.

**WRONG or internally inconsistent**

1. Sweep 1 says to build neatvnc with `-Dnettle=disabled` and use DES auth or no auth. These contradict each other, and the DES route is blocked. [read] https://raw.githubusercontent.com/any1/neatvnc/master/meson.build ties DES, RSA-AES and Apple-DH auth to the `nettle` option.
   - Without nettle, only None (and TLS via gnutls) remain.
   - wayvnc's README says macOS Screen Sharing refuses a None server. Sweep 3 cites that README line, and I did not re-open it.
   - So a macOS-first user needs nettle, hogweed and gmp on the device.
   - The same nettle option is also needed for WebSocket (noVNC).
   - The minimal "pixman + zlib + aml" set therefore only works for a None-auth server, or one reached through an SSH or USB tunnel.
2. The nettle requirement is `>=4.0 <5.0` in neatvnc master. No sweep mentions it.
   - Nettle 4.0 is very new and may not be in the OE release the peer builds against. [inf]
   - This is a build blocker candidate to check on the build machine.
   - I read this from a model-summarised fetch of meson.build, so confirm it in the file.
3. "80 KB/s Linux-to-Linux" is misattributed. [read] https://lkml.iu.edu/hypermail/linux/kernel/0510.2/1515.html shows it is Marcel Holtmann's remark ("you can get something around 80KB/sec"), not a measurement.
   - The only measurements in that thread are about 10 KB/s (Billionton CF card) and about 25 KB/s (USB dongle with a Nokia 6230).
   - Sweep 3 handled this correctly. Sweep 2 listed 80 KB/s as a "measured" figure and should be corrected.
4. Sweep 3's UART arithmetic does not agree with itself.
   - At 8N1, 115,200 baud moves 11,520 B/s, which sweep 3 states correctly.
   - But "1691 B × 8 / 115,200 = 117 ms" counts 8 bits per byte.
   - With start and stop bits (10 bits per byte), one full BNEP frame takes about 147 ms. The 117 ms comes from the UCL paper and ignores framing.
5. Sweep 4 says wayvnc "only logs an error" when the output-power global is missing. [read] https://raw.githubusercontent.com/any1/wayvnc/master/src/main.c shows a missing power global is non-fatal, but the code says "Capturing may fail". That matches the sweep's design conclusion that the capture source must always report power ON.

**CONFIRMED (not repeated in full)**

- Link-budget arithmetic is right, to the stated precision:
  - DH5 723.2 kbit/s (90.4 KB/s).
  - DM5 477.9 kbit/s.
  - Symmetric DH5 433.9 kbit/s.
  - 153,600 B takes 1.70 s at 90.4 KB/s and 2.83 s at 54.2 KB/s.
  - Video frame sizes and the 7.2–8.3 ms bus time per 240x136 frame are right.
  - The gadget peak of 9.728 Mbit/s is right.
- neatvnc option names and defaults (jpeg, tls, nettle, gbm, h264 all auto) are as reported.
- wlroots screencopy fails on a disabled output. Local tree: `types/wlr_screencopy_v1.c` lines 290, 364 and 525 check `output->enabled`. picowl creates no ext-image-copy-capture manager.

- UNSUPPORTED: no source gives any zlib, ZRLE, Hextile or JPEG speed for PXA255 or any ARMv5 core.
  - Every CPU figure (ZRLE 10–40 ms, JPEG 20–60 ms, Hextile 2–6 ms) is an extrapolation from one unopened ResearchGate snippet (gzip -1 on a Raspberry Pi, 1.87 MB/s).
  - Treat them as ±3x or worse.
- UNCHECKED: the claims below were not re-opened.
  - macOS Screen Sharing supports only Zlib and ZRLE (a weak HackTricks summary).
  - Apple-DH working against neatvnc.

- Behaviour on the real 0.19.0 tag was not checked on the web, but the local 0.19.0 checkout supports the screencopy claims above.

**Gaps the sweeps missed**

- **CDC EEM as a USB option.** EEM does not need altsettings, so it is not blocked the way ECM and NCM are on `pxa25x_udc`. Whether any macOS version ships an EEM host driver is UNCHECKED. If none does, a Mac can reach the device only through bt-pan or a Linux or Windows intermediate.
- **TCP_NODELAY and the pending-update cap** are needed on bnep0 to avoid latency blow-up. neatvnc's 33 ms in-flight ceiling is aggressive for a 10 KB/s link, as sweep 1 noted.
- **A neatvnc built into picowl needs aml's main loop** driven from the wl_event_loop. aml is also pthread-based, so this needs a small prototype.
- **TLS on the PXA255 is likely too expensive** without measurement. An SSH tunnel would add crypto CPU as well.

**Five most decision-relevant confirmed facts**

1. The display-off wish cannot be met by blanking the DRM output and running stock wayvnc.
   - Screencopy fails on a disabled output (local wlroots 0.19.0, lines 290, 364 and 525).
   - Today's blank path disables the output and stops rendering.
   - wayvnc also tries to switch the output power on at connect.
   - So an always-enabled RAM output is needed, either a headless output swap or an in-process neatvnc feed.
2. The bt-pan budget is 10–25 KB/s measured. Real figures on the h2200 are unknown.
   - The h2200 radio is Bluetooth 1.1, so the DH5 ceiling is 90.4 KB/s, and 80 KB/s is only an expert's claim.
   - A full raw RGB565 frame (153,600 B) takes 6–15 s at the measured rates. Compression and damage-only updates are mandatory.
3. neatvnc's encoder choice is only Raw, Tight or ZRLE, and Hextile and CopyRect are never emitted. ZRLE is the sensible one for UI content (sweep claim; I did not re-read `server.c`).
4. The auth and dependency trade-off decides the build. The minimal pixman, zlib and aml build means None auth only. macOS Screen Sharing needs DES, which needs nettle. A nettle `>=4.0 <5.0` pin may not exist in the OE tree.
5. No ARMv5 or no-FPU evidence exists for wayvnc or neatvnc. The first step is an on-device build and a zlib level 1 and `bench/zrle-bench` run, plus an iperf run over bnep0.
